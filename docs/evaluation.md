# Evaluation

How the benchmark is built, what the metrics mean, and how the system changed in response to it. Current numbers: [`eval/results/latest.md`](../eval/results/latest.md). Ablations: [`eval/results/comparison.md`](../eval/results/comparison.md).

## Corpus

`sample_data/` holds 29 synthetic documents about four fictional organizations and their projects:

* Quillon Labs: Project Halcyon (search) and the retired Project Atlas
* Brightwater Health: Project Lodestar (patient record linkage)
* Tessellate AI: Project Wren (on-device inference)
* Kestrel Logistics: Project Ember (route optimization)

| Format | Count | Examples |
|---|---|---|
| Markdown | 9 | design doc, ADR log, postmortem, RFC, security review, READMEs, onboarding guide |
| Plain text | 9 | meeting notes, email thread, standup log, call notes, announcement, agenda, trip report, memo |
| PDF | 5 | quarterly report, compliance audit, white paper, operations review, contract summary (generated by `scripts/generate_sample_pdfs.py`) |
| JSON | 7 | issue tracker export, team directory, vendor registry, benchmark runs, configuration, match rules, chat export |

The corpus is written to contain the phenomena the system targets:

* recurring entities under different surface forms ("Alice Chen", "A. Chen", "Dr. Chen", "Alice"; "Samuel Okafor", "Sam Okafor", "S. Okafor", "Sam")
* deliberate ambiguity (two Alices, two Sams)
* exact identifiers (`QL-5031`, `HAL-157`, `retrieval.hybrid_alpha`)
* facts that require a relationship hop (the Implementation section of the Lodestar RFC never says "Lodestar")
* near-miss distractors (Q3 revenue exists, Q4 does not; Lisbon van counts exist, Porto counts do not)

## Queries

`eval/datasets/queries.json` has 100 queries:

| Category | n | Probes |
|---|---|---|
| lexical | 20 | Identifiers, config keys, codes, rare tokens |
| semantic | 25 | Paraphrases with little vocabulary overlap |
| entity | 22 | Questions phrased through aliases or variant spellings ("A. Chen", "QuillonLabs", "S. Okafor") |
| relational | 15 | Answers that sit one relationship away from the named entity ("the project led by X") |
| unanswerable | 18 | 8 in-domain near misses, 5 unknown entities, 5 out-of-domain |

**Labels.** Each answerable query lists `relevant_sources` (filenames) and `evidence` strings. At evaluation time a chunk is relevant if it belongs to a relevant source and contains an evidence string (case- and whitespace-insensitive). The resolved document and chunk IDs are written into `latest.json` for every query. An evidence string that matches no chunk raises `DatasetIntegrityError`; a broken label can never silently count as a miss.

**Splits.** Every third query is `dev` (33), the rest `test` (67). Tuning is meant to use dev only; both splits are reported.

**Caveat.** The corpus and queries were written by the same author as the system. Category proportions are a design choice, and the averages depend on them; the per-category tables are the more informative view.

## Metrics

* **Recall@k**: |relevant ∩ top-k| / |relevant|, averaged over answerable queries. Most queries have one relevant chunk; some have two or three.
* **Hit@k**: 1 if any relevant chunk is in the top k.
* **MRR**: 1 / rank of the first relevant chunk within the top 10 (0 if none).
* **nDCG@10**: binary relevance.
* **Source accuracy@1**: the top chunk comes from a relevant document.
* **Latency**: wall-clock time of `engine.search` (query embedding, all retrievers, scoring, reranking, confidence), after 3 warm-up queries per mode; mean / p50 / p95 over all 100 queries.
* **Abstention** (all queries; positive class = unanswerable): precision, recall, F1, false-abstention rate on answerable queries, and Hit@5 on the answerable queries that were answered.
* **Entity resolution**: each hand-labelled gold mention (source file, surface) is mapped to the majority entity of the matching extracted mentions. Pairwise precision/recall/F1 are computed over all mention pairs and compared with exact-string and normalized-name clustering. Coverage is the share of gold mentions the extractors found.

## Reproducing

```bash
python scripts/run_eval.py --backend postgres                   # eval/results/latest.{json,md}
scripts/reproduce_results.sh                                     # everything in eval/results/
python scripts/sweep_confidence.py eval/results/latest.json     # threshold sweep from recorded confidences
python scripts/compare_results.py eval/results/*.json            # side-by-side table
```

Each run reindexes `sample_data/` from scratch with the configuration given through environment variables. Retrieval metrics are deterministic; latencies vary by a few percent between runs.

## Development log

The benchmark shaped the system. These are the changes it drove, recorded honestly.

**1. First full run: the entity signal made things worse.** On an earlier revision (memory backend), Hybrid + Entity scored *below* plain hybrid: Recall@5 0.884 vs 0.896, MRR 0.740 vs 0.756, and relational Hit@5 0.667 vs 0.800. That revision no longer exists, but disabling the two later additions with configuration flags reproduces it closely (PostgreSQL backend, current code):

| Hybrid + Entity configuration | Recall@5 | MRR | Relational Hit@5 | Result file |
|---|---|---|---|---|
| no graph expansion at all | 0.872 | 0.746 | 0.600 | `ablation_no_graph_expansion` |
| no header context, no type hints (≈ first run) | 0.884 | 0.743 | 0.667 | `ablation_no_header_no_hints` |
| no header context | 0.890 | 0.744 | 0.733 | `ablation_no_header_context` |
| no type hints | 0.896 | 0.746 | 0.733 | `ablation_no_type_hints` |
| default | 0.927 | 0.751 | 0.933 | `latest` |
| *(plain hybrid, for reference)* | *0.902* | *0.751* | *0.800* | `latest` |

Per-query error analysis showed two causes:

* Section paragraphs often never name their subject. The "Implementation" section of the Lodestar RFC mentions Rust and Kafka but not Lodestar, so the graph could not connect it to Ravi Narayan's project. **Fix:** header-context entities, i.e. entities in a chunk's title/section header count as context entities of the chunk and participate in relationship extraction.
* Chunks that merely mention the queried person received the maximum entity score and crowded out the chunk about that person's project. **Fix:** type-hinted expansion. When the query names the neighbor's type ("the *project* led by…"), the 1-hop neighbor receives the full edge weight instead of the 0.6 decay.

These fixes were designed while looking at this dataset, so they are not independent evidence. The dev/test split is reported to partially compensate: on the test split, Recall@5 is 0.927 (Hybrid + Entity) vs 0.909 (Hybrid), with equal MRR.

**2. Bugs the evaluation caught.**

| Symptom in the results | Cause | Fix |
|---|---|---|
| Harness refused to run: two evidence strings ("ADR-009: HNSW index parameters") matched no chunk | The Markdown parser kept headings only as metadata, so they were missing from the provenance text | Headings stay in the document text and are packed with their section |
| Abstention recall 0.333 on PostgreSQL vs 0.556 in memory for the same queries | SQL scoping bug in `unknown_terms`: inside the subquery, `lexeme` resolved to the inner table's column, so every term looked known | Aliased the outer column; regression test in `test_postgres.py` |
| Lexical p95 ≈ 40 ms on PostgreSQL vs < 1 ms in memory | The BM25 query re-scanned `lexeme_stats` once per matched chunk | IDF computed once in a `MATERIALIZED` CTE and hash-joined: ≈ 1.7 ms |
| ER gold coverage dropped and "Samantha Reyes" vanished as an entity | After headings entered chunk text, spaCy's small model missed names right after a heading line | NER runs per paragraph with heading lines excluded; regression tests |
| Spurious `related_to` edges (Alice Chen ↔ Alfama) | The hard-wrap heuristic chained short agenda lines into one "sentence" | Wrap detection keys on the raw previous line's length; time-prefixed lines count as items |

## Confidence threshold

`eval/results/confidence_sweep.md` recomputes abstention at thresholds 0.30–0.70 from the recorded confidences and gate decisions, selects on dev and reports test. For Hybrid + Entity the hard gates do most of the work: dev F1 is flat from 0.30 to 0.45. The dev split contains only 6 unanswerable queries, so the dev-optimal threshold is noisy. The a-priori default of 0.45 was kept rather than fitted.

What abstention can and cannot do here:

* **caught:** out-of-domain questions (weak-evidence gate) and questions about unknown people, organizations, projects or locations (unknown-entity gate)
* **missed:** in-domain near misses ("Q4 revenue" when only Q3 exists). The retrieved evidence is on-topic and strong, so evidence-level signals cannot tell the difference. Answer-level verification is the fix (future work).

## Extending the dataset

Add entries to `eval/datasets/queries.json`:

```json
{"id": "q101", "query": "…", "category": "semantic", "answerable": true, "split": "test",
 "relevant_sources": ["some_file.md"], "evidence": ["a short verbatim phrase from the answer passage"]}
```

Keep evidence strings short enough to sit inside one chunk; the harness reports any that do not match. For a new corpus, point `--data` at its directory and `--dataset` at a matching file; `relevant_chunk_ids` / `relevant_document_ids` may be given explicitly instead of evidence strings.
